### **Интеграции между сервисами**

#### 1. Брокер сообщений на ферме: Mosquitto, протокол MQTT

Обоснование: MQTT разработан для IoT-устройств с ограниченными ресурсами. Mosquitto нетребователен к памяти и работает на локальном оборудовании фермы. Кормушки, поилки и датчики разных производителей поддерживают MQTT как стандартный протокол. Для устройств с Modbus адаптер на фермовом агенте выполняет трансляцию Modbus в MQTT.

Компромисс: Mosquitto не гарантирует порядок сообщений и не хранит историю. Для гарантированной доставки используется QoS 1, что допускает дубликаты. Дедупликация выполняется на стороне получателя.

#### 2. Брокер сообщений в центре: Apache Kafka, существующий

Обоснование: повторное использование инфраструктуры компании. Kafka обеспечивает пропускную способность, достаточную для агрегации событий со всех ферм. Хранение истории событий позволяет восстановить состояние после сбоя.

Компромисс: Kafka требует выделенной памяти и дискового пространства. Для MVP это оправдано, так как инфраструктура уже развёрнута и поддерживается.

#### 3. Синхронизация между фермой и центром: HTTPS и Kafka

Обоснование: агент синхронизации на ферме использует HTTPS для операций "запрос-ответ": получение конфигураций и обновлений ML-модели. Потоковые данные, такие как события аналитики и показания датчиков, передаются через Kafka-продюсер на агенте. При потере связи события буферизируются в SQLite и отправляются после восстановления.

Компромисс: два протокола синхронизации усложняют реализацию. HTTPS используется для операций, требующих подтверждения доставки. Kafka используется для потоковых данных с гарантией порядка.

#### 4. Протокол видеопотока: RTSP

Обоснование: RTSP поддерживается большинством IP-камер разных производителей. Адаптер устройств на ферме подключается к камерам по RTSP и передаёт кадры в контейнер видеоаналитики.

Компромисс: RTSP работает поверх TCP/UDP и чувствителен к задержкам сети. На локальной сети фермы между камерой и сервером задержка минимальна. В альтернативном решении для передачи видео на центральный сервер используется WebRTC со сжатием, что увеличивает задержку.

#### 5. Взаимодействие с кормушками и поилками: MQTT и Modbus

Обоснование: производители используют MQTT или Modbus. Адаптер устройств поддерживает оба протокола и публикует команды через локальный MQTT-брокер. Для Modbus-устройств адаптер выполняет трансляцию протоколов.

Компромисс: поддержка двух протоколов увеличивает сложность адаптера. При подключении устройства нового производителя может потребоваться новый адаптер.

#### 6. API для веб-портала и мобильного приложения: REST и WebSocket

Обоснование: REST API через Kong для типовых операций чтения и записи: расписания, устройства, пользователи. WebSocket через Redis для обновлений в реальном времени: оповещения и текущее состояние видеоаналитики.

Компромисс: WebSocket требует постоянного соединения и увеличивает нагрузку на API Gateway. Для MVP количество одновременных подключений невелико.

#### 7. Хранение данных на ферме: SQLite

Обоснование: SQLite не требует отдельного процесса, потребляет минимум ресурсов. Объём данных одной фермы: буфер событий и конфигурации. Этот объём укладывается в возможности SQLite.

Компромисс: SQLite ограничивает одновременную запись одним потоком. На фермовом агенте запись выполняет агент синхронизации, поэтому ограничение допустимо.

#### 8. Хранение операционных данных в центре: PostgreSQL

Обоснование: PostgreSQL хранит реестр устройств, пользователей, ролей, расписаний кормления и данных о поголовье. Для аналитических запросов данные передаются в существующий ClickHouse.

Компромисс: два хранилища, PostgreSQL и ClickHouse, усложняют инфраструктуру. ClickHouse уже развёрнут в компании и используется для хранения данных временных рядов.

#### 9. Аутентификация и авторизация: Keycloak. Формат ML-модели: ONNX

Keycloak поддерживает OAuth 2.0, OIDC и RBAC. Покрывает требование к современным способам аутентификации. Требует JVM и отдельного экземпляра PostgreSQL, что для MVP избыточно. Опыт команды с Keycloak требует оценки.

Формат модели: ONNX. Обеспечивает переносимость между CPU, NVIDIA GPU через TensorRT и периферийными ускорителями NPU. Конвертация модели от партнёров в ONNX может потребовать дополнительной работы. Выбор среды выполнения зависит от конкретного оборудования на фермах, которое пока не определено.

### **Недостатки, ограничения, риски**

**Основное решение, распределённое:**

1. Стоимость оборудования. Сервер с GPU/NPU на каждой ферме стоит дороже, чем тонкий агент. Затраты на оборудование растут линейно с количеством ферм.

2. Обновление ML-модели на всех агентах. При нестабильной связи доставка модели размером в сотни мегабайт может занять часы. В это время разные фермы работают с разными версиями модели.

3. Разнородность оборудования. Разные фермы могут получить разные ускорители: NVIDIA Jetson, Intel NCS и другие. Каждая платформа требует отдельной сборки и тестирования.

4. Обслуживание на местах. При аппаратном сбое локального сервера требуется выезд специалиста на ферму или наличие запасного оборудования.

5. Два брокера сообщений. На ферме используется Mosquitto с протоколом MQTT, в центре Apache Kafka с протоколом Kafka Protocol. Разные протоколы увеличивают сложность разработки и отладки.

**Альтернативное решение, централизованное:**

1. Зависимость видеоаналитики от канала связи. При нестабильном WiFi видеопоток прерывается, и ML-инференс останавливается. Требование 5 секунд на оповещение может не выполняться.

2. Пропускная способность. Один поток H.264 720p занимает 2-4 Мбит/с. При 4-8 камерах на ферме канал должен обеспечивать 8-32 Мбит/с.

3. Отсутствие видеоаналитики в автономном режиме. Тонкий агент оповещает дежурного только по пороговым правилам датчиков. Детекция драк, задавливания поросят и оценка состояния животных при потере связи невозможны.

4. Единая точка отказа GPU-кластера. Выход из строя GPU-кластера останавливает видеоаналитику на всех фермах одновременно. Резервирование GPU-кластера увеличивает стоимость.

5. Задержка обработки. Путь от камеры на ферме до оповещения включает сжатие, передачу по сети, декодирование на центре, ML-инференс и отправку оповещения. Суммарная задержка может превысить 5 секунд.
